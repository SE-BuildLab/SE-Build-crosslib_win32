## 5. Source code reading summary / 入力ソースコード読解結果

- (EN) In 1.1.1w crypto/rsa/rsa_ossl.c rsa_ossl_private_decrypt() performs the RSA private operation and then dispatches on 'padding' to RSA_padding_check_PKCS1_type_2() (constant-time check since CVE-2022-4304 fixes) which still returns -1 on bad padding; crypto/rsa/rsa_pmeth.c pkey_rsa_decrypt() propagates this result in a constant-time way but the result itself is the oracle. ### Vulnerability mechanism (as observed in the code) / 脆弱性のメカニズム (コード上の観察)

[EN] In pristine 1.1.1w, `rsa_ossl_private_decrypt()` (crypto/rsa/rsa_ossl.c) handles `RSA_PKCS1_PADDING` by calling `RSA_padding_check_PKCS1_type_2()` (crypto/rsa/rsa_pk1.c). That function is constant time internally (CVE-2022-4304 hardening), but when the decrypted block is not `00 02 || >=8 non-zero bytes || 00 || message` it returns -1; the caller then queues `RSA_R_PKCS_DECODING_ERROR` / `RSA_R_PADDING_CHECK_FAILED` and `RSA_private_decrypt()` / `EVP_PKEY_decrypt()` fail without output. The validity of the padding is therefore an explicit API signal (return value, output length, error queue, application behaviour), which is the oracle needed by Bleichenbacher / Marvin chosen-ciphertext attacks against RSAES-PKCS1-v1_5. The IPALongPatch 003 (semantic port of Ubuntu's `openssl-1.1.1-pkcs1-implicit-rejection.patch`, i.e. the Red Hat back-port of OpenSSL 3.2's PR #13817) makes `RSA_PKCS1_PADDING` compute, unconditionally, `kdk = HMAC-SHA256(SHA256(d padded to |n|), ciphertext padded to |n|)` and call the new `ossl_rsa_padding_check_PKCS1_type_2()`, which derives a synthetic message and a pseudo-random length from `kdk` with `ossl_rsa_prf()` and selects the real or the synthetic message with constant-time masks, so the API always "succeeds". The old behaviour is kept as padding mode `RSA_PKCS1_NO_IMPLICIT_REJECT_PADDING` (8), reachable through the new ctrl `EVP_PKEY_CTRL_RSA_IMPLICIT_REJECTION` / `rsa_pkcs1_implicit_rejection:0` (crypto/rsa/rsa_pmeth.c), and is forced for engine keys (`RSA_FLAG_EXT_PKEY`) and by crypto/cms/cms_env.c and crypto/pkcs7/pk7_doit.c, whose callers need the error to detect a non-matching key.

[JA] 素の 1.1.1w では `rsa_ossl_private_decrypt()` (crypto/rsa/rsa_ossl.c) が `RSA_PKCS1_PADDING` に対して `RSA_padding_check_PKCS1_type_2()` (crypto/rsa/rsa_pk1.c) を呼ぶ。この関数は内部的には定数時間 (CVE-2022-4304 の強化) だが、復号ブロックが `00 02 || 8 バイト以上の非ゼロ || 00 || メッセージ` の形でない場合は -1 を返し、呼び出し側は `RSA_R_PKCS_DECODING_ERROR` / `RSA_R_PADDING_CHECK_FAILED` をキューに入れ、`RSA_private_decrypt()` / `EVP_PKEY_decrypt()` は出力無しで失敗する。したがってパディングの正否が明示的な API 信号 (戻り値・出力長・エラーキュー・アプリケーションの挙動) になっており、これが RSAES-PKCS1-v1_5 に対する Bleichenbacher / Marvin 選択暗号文攻撃に必要なオラクルである。IPALongPatch 003 (Ubuntu の `openssl-1.1.1-pkcs1-implicit-rejection.patch`、すなわち OpenSSL 3.2 の PR #13817 の Red Hat バックポートの意味的移植) は、`RSA_PKCS1_PADDING` の場合に常に `kdk = HMAC-SHA256(|n| 長にパディングした d の SHA256, |n| 長にパディングした暗号文)` を計算し、新設の `ossl_rsa_padding_check_PKCS1_type_2()` を呼ぶ。同関数は `ossl_rsa_prf()` で `kdk` から合成メッセージと疑似乱数長を導出し、定数時間マスクで本物か合成かを選択するため、API は常に「成功」する。従来動作はパディングモード `RSA_PKCS1_NO_IMPLICIT_REJECT_PADDING` (8) として残され、新 ctrl `EVP_PKEY_CTRL_RSA_IMPLICIT_REJECTION` / `rsa_pkcs1_implicit_rejection:0` (crypto/rsa/rsa_pmeth.c) で選択でき、エンジン鍵 (`RSA_FLAG_EXT_PKEY`) と、鍵不一致の検出にエラーを必要とする crypto/cms/cms_env.c および crypto/pkcs7/pk7_doit.c では強制される。

### Limitations / notes / 制約・注記

[EN] (1) No CVE is assigned to OpenSSL for this item (the Marvin page lists "OpenSSL (API level): No CVE"); the issue is an API-level oracle, so there is no crash/ASan/gdb artefact — the evidence is behavioural.
